## Problem & user

RocketShip PMs need this handled: Juno is an AI Associate PM that gives a specific PM a weekly, evidence-linked view of recurring NPS feedback for the Collaboration & meetings area they own, related Webex discussions and Jira issues, and a source-linked ticket draft when no clear issue match exists.. Juno does this inside limits a human set on purpose, and defends every call it makes.

## 01 Context · Data Requirements

**Required sources, and exclusions**

For the selected PM, product area, and date window, use NPS records with comment text, record ID, and timestamp; relevant Webex Spaces and Direct messages; and matching Jira issues with current status and links. Use only the approved, dated copy of RocketShip’s strategy and roadmap as context. Do not search unrelated product areas or treat strategy documents as evidence that a user reported a problem.

Before production, name and verify the actual NPS system and Jira project. The sketch does not identify them, so they remain setup dependencies rather than assumed sources. Do not use other internal documents, external sources, or data the PM cannot access.

**How fresh must it be**

Run against the exact date window shown in the digest. Include source changes available before the run and fetch Jira status again immediately before rendering. A new record appears in the next digest; a prior digest is not current evidence.

If a source is unreachable, retry once for a temporary error. If it remains unavailable, identify the missing source, mark the digest incomplete, and omit claims that depend on it. Do not substitute cached or inferred records.

## 02 Tools · System Capabilities

**The verb list**

- **Read:** Read and search the PM-authorized NPS, relevant Webex Spaces and Direct messages, Jira issues, and the approved dated strategy and roadmap.
- **Analysis:** Group similar comments, compare evidence, classify Jira matches as clear, uncertain, or unmatched, and attach source links to each claim.
- **Draft:** Prepare a source-linked Jira ticket draft, including reproduction notes, for the PM to review. The draft is shown in the digest and is not created in Jira.
- **Write / send:** No Jira issue creation or edits, assignment, priority changes, Webex messages, or replies. Juno cannot promise dates or speak on the PM’s behalf.

**Deliberate omissions**

Juno has no Jira write or Webex send tool. A mistaken issue or message could create duplicate work, change team priorities, or be mistaken for the PM’s decision. A draft is reviewable and easy to discard; a write or sent message can affect other people and may be difficult to fully undo. The PM can make those changes after review.

## 03 Loop · AI Costs & Latency

**Turn ceiling and escalation**

Run one bounded scan of the selected weekly feedback period, followed by one pass to check possible Jira matches and source links. Allow at most one retry for a temporary source error. Stop and report the gap if a source remains unavailable. Leave ambiguous or conflicting evidence for the PM; do not keep searching or guess.

**Latency and cost target**

Proposed pilot target: 95% of weekly digests render within five minutes of the run starting. Keep each digest to at most two analysis passes and one retry per temporarily failing source. Set a pilot ceiling of **$0.50 per digest** for model and retrieval costs; record actual cost and p95 completion time, then revisit the ceiling after the first four weeks using observed comment volume. If the ceiling or time target is exceeded, return an incomplete digest with the affected coverage identified.

## 04 Memory · Data Requirements

**What persists, at what scope**

NPS comments and source conversations remain in their source systems; Juno does not retain them as long-term memory. Run data is discarded after the digest is produced. The weekly digest is temporary and is replaced by the next digest; if no new digest is produced, retain it for no more than 14 days and label its date window.

A PM’s explicit corrections and preferences persist only for that PM and product area until that PM changes or deletes them. They are not shared with other PMs. Do not store inferred preferences as memory.

**Expiry and write rules**

Source records are authoritative for what was said and when. A PM’s explicit correction takes precedence over Juno’s prior interpretation or grouping, but it does not alter the source record or erase its citation. Keep each correction until the PM changes or deletes it; keep run data only through digest generation and the digest until replacement or the 14-day limit. When a correction conflicts with current source evidence, show the conflict and ask the PM to resolve it.

## 05 Permissions · AI Risks & Mitigations

**The permission tier**

| Side-effect class | Tier |
|---|---|
| read | auto |
| draft | auto |
| write | confirm |
| send | blocked |

**Justification**

- **Read — automatic:** Read only sources the PM is already authorized to access.
- **Draft — automatic:** Prepare summaries and a Jira ticket draft for the PM to review; do not save it as an issue.
- **Write — blocked:** Juno cannot create or edit Jira issues, assign work, or change priorities or dates.
- **Send — blocked:** Juno cannot send Webex messages or replies.

New source access or a new permission model requires separate approval and review. The PM must decide uncertain matches and any proposed reply, assignment, escalation, priority, date, or Jira write.

## 06 Verification · AI Testing & Measurement

**The check before output ships**

- Reconcile the displayed NPS comment count exactly against the records returned for the selected PM, product area, and date window.
- Require a working source link for every evidence-based summary claim and every ticket-draft step; if a link cannot be checked, mark that evidence unavailable.
- Fetch Jira status immediately before rendering and show when it was checked.
- Label every possible Jira match **clear**, **uncertain**, or **unmatched**. Do not present an uncertain match as fact.
- Check for missing, stale, or conflicting evidence and visibly flag it.

Target: all displayed counts reconcile, all evidence-based claims have source links, and every match has a label. Do not show a digest as complete if any check fails.

**Failure behaviour**

If a check fails, mark the digest **incomplete** and state which check failed and which source or claims are affected. Remove or clearly mark unsupported claims and omit any ticket draft whose reproduction notes cannot be traced to sources. Show unaffected, verified sections when useful; do not silently drop the whole digest or present failed checks as passed. Hand ambiguous or conflicting cases to the PM for review.
